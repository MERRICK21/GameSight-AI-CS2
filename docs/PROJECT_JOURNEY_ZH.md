# GameSight AI for CS2：项目经历与完整心路历程

## 一句话介绍

GameSight AI 将普通 CS2 第一视角录像转换为可审计的回合、个人击杀/死亡、
交战证据和情境化教练建议，系统组合了确定性计算机视觉、四层 RAG 知识库、
受约束 LLM，以及只能调用只读工具的单 Agent。

## 为什么项目会这样演进

这个项目并不是从“我要做一个 LLM 应用”开始的。最初的问题是：在没有
`.dem` 文件的情况下，能否仅从玩家录制的第一视角视频中，恢复足够可靠、
能够让用户复核的比赛结构？

因此项目的推进顺序是：

1. 先建立模块边界、领域模型和 Sprint 计划。
2. 完成视频读取、HUD 识别和时序事件重建。
3. 解决真实录像中的误检、漏检、超时和创作者 UI 噪声。
4. 在事实可审计之后，先实现确定性的规则教练。
5. 再加入 RAG 和 LLM，但不让 LLM 负责发现事实。
6. 最后才增加单 Agent，让它调用已经成熟的证据和知识工具。

这条路径体现了一个核心原则：模型能力必须建立在可靠数据、权限边界和失败
回退之上，而不是先引入 Agent 概念，再寻找它能够解决的问题。

## 第一阶段：用 Sprint 建立工程基础

项目初期被拆成多个独立、可测试的 Sprint：

- Sprint 1：视频输入、格式验证、元数据读取和帧采样。
- Sprint 2：HUD 感知层，分别解析准星、生命值、击杀信息、金钱和回合状态。
- Sprint 3：时序事件引擎和回合状态机。
- Sprint 4：可选 YOLO 玩家检测和敌我阵营识别。
- Sprint 5：目标跟踪和检测关联。
- Sprint 6：类型化时间线和 JSON 导出。
- Sprint 7：带证据链接的比赛报告。
- Sprint 8：Streamlit 网站产品化。
- Sprint 9：中英文国际化。
- Sprint 10：规则 AI 教练。
- Sprint 11：事件截图和复盘视频片段。

感知、事件推理、报告和 UI 之间不直接传递任意字典，而是使用 Pydantic 领域
模型。这一选择后来成为 RAG 和 Agent 工具化的基础：Agent 可以读取稳定的
`AnalysisResult`、`RoundAnalysis` 和 `DecisionContext`，不需要理解视觉模块内部实现。

## 第二阶段：从“识别画面”到“重建比赛”

在真实录像测试中，系统曾出现过许多表面上合理、实际错误的结果：

- 19 分钟录像被识别成一个回合。
- 持续显示的同一条击杀信息被重复统计。
- 稀疏采样漏掉瞬间出现的狙击枪击杀。
- 正常白色生命数字被误判成 HUD 消失，从而产生假死亡。
- 录像作者的水印、键位显示和语音 UI 干扰画面变化统计。
- 高帧率分析整段视频导致运行超时，最终结果反而不完整。

解决方案并不是简单提高采样帧率或换一个更大的模型，而是组合多种原生 HUD
证据和时序约束：

- 通过比分变化、计时器连续性和回合状态重建回合边界。
- 通过 CS2 原生本地玩家击杀高亮归因个人击杀。
- 通过底部生命 HUD 和顶部选中玩家卡片归因第一视角死亡。
- 使用防抖、持续状态指纹和多杀行跟踪，避免重复计数。
- 采用全视频低帧率扫描和候选窗口高帧率细化的两阶段分析。
- 对创作者覆盖层使用局部屏蔽和鲁棒分块统计，而不是识别创作者名字。
- 建立轻量级比赛真值夹具，长期保护 20/10 和 25/14 等已确认结果。

这一阶段形成了整个项目最重要的工程标准：每个事件都必须保留时间、置信度、
来源和可查看证据；无法确认的信息必须保持未知。

## 第三阶段：为什么先做规则教练

在加入 LLM 之前，项目先实现了 `RuleBasedCoach`。它能够针对白屏、连续架镜、
遇敌、疑似交战和死亡窗口给出中立复盘建议，并在缺少地图、阵营、经济或位置
证据时主动放弃具体战术结论。

真实测试暴露出几个关键问题：

- 首次遇敌占一个短回合的 42%，不代表玩家推进缓慢。
- 回合刚开始、尚未接敌时，不应直接判断准星不稳定。
- 第一回合拥有 100 护甲但没有头盔，不意味着购买决策错误。
- 视角运动强度只能描述转身和跑图，不能自动代表瞄准质量。

因此，首次接敌时间、回合时长和视角活动度被降级为描述性证据。只有当地图、
阵营、出生点、路线、回合时钟等上下文足够时，系统才允许生成快慢、转点、
站位或购买结论。

## 第四阶段：受证据约束的 RAG + LLM

直接把检测结果和一篇 CS2 文章交给 LLM，会产生“听起来专业但依据不足”的建议。
因此 LLM 被明确移出事件发现环节，系统变成：

```text
视频/HUD 感知
  -> 类型化事件和回合上下文
  -> 确定性规则建议
  -> 情境优先的知识检索
  -> LLM 语言增强
  -> 引用、上下文、数字、版本和措辞校验
  -> 校验失败时回退规则教练
```

DeepSeek 是首发云端模型，Ollama 保留为本地适配器；中英文知识使用多语言
MiniLM 向量和 Chroma 持久化索引。

### 为什么不能把所有知识放在一个普通 Markdown 库中

下面两句话的权威程度完全不同：

- “CT 成功拆除炸弹会赢得回合。”这是游戏硬规则。
- “5v4 时通常不应进行无必要的单挑。”这是高概率正确的战术原则。

如果不区分，LLM 很容易输出“5v4 禁止前压”这种过度绝对的结论。因此知识库
被拆成四层：

- `game_rules`：胜利条件、Bomb 和固定机制。
- `tactical_fundamentals`：补枪、交叉火力、默认控图等通用原则。
- `situation_decisions`：残局、回防、保枪、低时间和人数优劣决策。
- `dynamic_game_data`：武器价格、击杀奖励和版本敏感经济数据。

每个知识块还携带一种规则强度：

- `hard_rule`
- `strategic_principle`
- `contextual_recommendation`

只有硬规则可以使用绝对措辞。战术原则必须保留“通常、倾向于、除非”等限定，
情境建议则必须匹配录像中真正已知的状态。

### 为什么要单独处理动态数据

CS2 的价格和奖励可能随版本改变，因此动态数据使用稳定知识 ID，并保存来源、
最后核验日期、生效日期和可选失效日期。缺少来源、无法核验或已经过期的数据
不会进入最终生成，避免旧经济数字被永久缓存为“规则”。

### 评价决策，而不是评价结果

每条 LLM 建议都必须声明：

```text
evaluation_basis = decision_quality
```

系统会拒绝“因为拿到击杀，所以这个决策正确”“因为输了残局，所以不应该尝试”
等结果论。评价依据是玩家在动作发生时能够掌握的信息，而不是事后结果。

## 第五阶段：单 Agent 与受控工具调用

完成 RAG 后，项目没有为了简历直接堆叠多 Agent，而是先实现一个边界清晰、
可以量化评估的单 Agent。它沿用现有 JSON LLM 和 Pydantic，不引入 LangChain
或 LangGraph 依赖。

Agent 只能调用五个只读工具：

1. `get_match_overview`：读取比赛概览和能力标志。
2. `list_coaching_candidates`：读取规则教练产生的不可变候选建议。
3. `get_round_evidence`：读取指定回合的事件和脱敏证据。
4. `get_decision_context`：读取已知上下文并明确列出未知字段。
5. `search_knowledge`：针对指定建议 ID 检索四层知识。

Agent 没有文件系统、Shell、网络、事件修改或报告写入工具。运行时最多三轮、
十二次工具调用；工具参数经过 Schema 验证，调用 ID 不得重复，工具观察结果有
大小预算，私有截图路径不会进入模型上下文。

工具输出和检索文章被明确视为“不可信数据”，不能作为修改协议、调用未知工具、
泄露 Prompt 或绕过校验的指令。Agent 若没有为某条建议调用知识检索，就不能在
最终答案中引用知识并增强该建议。

Agent 完成后仍需通过原有校验：

- 引用必须来自对应建议调用得到的知识块。
- 不得引入来源中不存在的数字。
- 不得使用缺失的地图、经济、位置或回合状态。
- 战术原则不得被绝对化。
- 动态数据必须处于有效核验周期。
- 不得用结果证明决策质量。

任何失败都会保留规则教练结果，并在界面展示 Agent 迭代次数、工具调用、工具
失败、使用过的工具、Token、延迟和停止原因。

## 当前完整架构

```text
CS2 第一视角录像
  -> 视频输入与自适应采样
  -> HUD / 第一视角 / 可选 YOLO 感知
  -> 时序事件引擎与回合重建
  -> 证据报告 + RuleBasedCoach 候选建议
  -> Single Replay Coach Agent
       -> 比赛概览工具
       -> 规则候选工具
       -> 回合证据工具
       -> 决策上下文工具
       -> 四层 RAG 检索工具
  -> 证据与策略校验器
  -> 中英文 Streamlit 报告，失败则回退确定性建议
```

## 可直接放入简历的描述

**GameSight AI for CS2｜基于视频理解、RAG、LLM 与单 Agent 的第一视角复盘教练**

- 构建端到端 CS2 第一视角录像分析系统，结合 OpenCV、OCR、可选 YOLO、时序
  事件重建和证据片段，支持回合恢复、个人击杀/死亡归因和中英文复盘报告。
- 设计四层 RAG 架构，使用多语言 MiniLM 与 Chroma 分离游戏硬规则、战术原则、
  情境决策和版本敏感数据，并实现情境优先检索与 Recall@K/MRR 离线评估。
- 实现 DeepSeek 首发、Ollama 兼容的结构化 LLM 层，通过引用白名单、未知数字
  检测、上下文弃权、动态数据时效和确定性回退控制幻觉。
- 开发具有五个只读工具的单 Agent，加入类型化工具协议、三轮/十二次调用预算、
  私有路径脱敏、Prompt 注入防护和完整调用诊断，避免不必要的多 Agent 复杂度。
- 引入基于决策质量而非最终结果的评价约束，拒绝将击杀或获胜直接当作操作正确
  的证明。
- 建立 534 项自动化回归测试，覆盖视觉事件、比赛 K/D、RAG 检索、LLM 校验、
  Agent 权限、工具轨迹与失败回退。

## 面试中的完整叙述

> 我一开始把项目定义为视频理解问题，而不是 LLM Demo。第一阶段先通过 Sprint
> 拆解完成视频输入、HUD 感知、事件重建、证据报告和网站，并用真实录像解决
> 回合数、击杀去重、稀疏采样漏检、死亡归因和创作者覆盖层噪声。所有事件都
> 保留时间、置信度和证据，因此后续模型不需要猜发生了什么。
>
> 在事实层稳定以后，我先做规则教练，然后发现即使规则建议也可能因为上下文
> 不足而误判推进速度、准星或经济。于是我加入 RAG，但没有把所有知识放在一个
> 普通语料库，而是分为硬规则、战术基础、情境决策和动态数据四层，并通过规则
> 强度和版本元数据控制 LLM 能够说多绝对。
>
> 最后我实现了单 Agent。它可以决定是否读取比赛概览、回合证据、决策上下文
> 以及检索什么知识，但没有文件、网络和数据修改权限。整个循环有明确预算和
> 工具 Schema，结束后还要通过原来的证据校验。如果失败就回退规则教练。我没有
> 一开始就使用多 Agent 或 Agent 框架，因为当前流程还不需要那种复杂度；我更想
> 证明 Agent 的工具选择、权限、状态和失败处理是可靠的。

## 这段经历真正体现的能力

- 能把模糊产品想法拆成可验证的 Sprint 和模块边界。
- 能从真实数据错误中定位问题，而不是只在合成样例上优化。
- 理解计算机视觉、时序推理、RAG、LLM 和 Agent 各自应该负责什么。
- 知道 Agent 设计首先是状态、工具权限、预算和可观测性问题，而不只是 Prompt。
- 能诚实管理不确定性，在证据不足时弃权，在生成失败时提供可用回退。
- 能用自动化测试和真实真值持续保护已经解决的问题。

## 当前限制与下一步

- 这是有边界的单模型 Agent，不是多 Agent 系统。
- Agent 操作结构化证据，不会自主读取原始视频帧。
- 存活人数、可靠 Bomb/拆弹器状态和完整经济仍依赖未来感知能力或用户输入。
- 下一步最有价值的是建立 Agent 离线评测集，衡量工具选择、参数正确率、引用
  可靠性、应当弃权的场景和最终教练质量。
- 只有当独立 Evidence、Retrieval、Coach、Critic 角色能够通过评测证明收益时，
  才考虑进一步拆分为多 Agent。
